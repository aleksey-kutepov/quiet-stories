# Security policy and model

## Reporting a vulnerability

Please use [GitHub private vulnerability reporting](https://github.com/aleksey-kutepov/quiet-stories/security/advisories/new) for authentication, session, navigation, or privacy vulnerabilities. Include the affected revision, device and OS, expected behavior, and a minimal reproduction using synthetic data.

If the private reporting form is unavailable, open an issue titled **Request private security contact** without vulnerability details so the maintainer can arrange a private channel. Do not put credentials, cookies, recovery codes, account identifiers, private messages, or exploit details in a public issue or pull request.

Security fixes target the latest development version. Older releases have no separate maintenance commitment. This is a community project with no guaranteed response time; ordinary layout or compatibility bugs can use public issues with personal data removed.

## Security model

Stories is a personal-use, restricted WebKit browser. It reduces distractions without operating an intermediary for Instagram account data. Instagram and the application itself remain trusted; this is not a hardened boundary against either.

## Data boundaries

- Credentials are entered into Instagram's HTTPS page. There is no native credential form, OAuth-token store, HTTP proxy, password logging, or app-owned telemetry.
- Login, reset, and challenge routes use a separate authentication web view with no app user scripts or native bridge. Authentication and filtered Stories/Messages views share the session's WebKit data store. Native navigation replaces the view when changing between them, including authentication reached through client-side navigation.
- Authentication submissions to a supported content route complete their original request while the authentication view stays hidden; response policy then opens a filtered view using GET. Native request transfers preserve the original request, permit non-GET/HEAD transfers only from a trusted Instagram main frame, and refuse transfers when WebKit supplies no form body. Application code neither parses nor logs that body. Response handoffs do not replay form submissions.
- App code does not call cookie-reading APIs, extract input values, download story media, or persist page content outside WebKit. WebKit handles cookies and normal website requests. An unscripted authentication view reduces accidental credential exposure; it cannot make access impossible for modified application code.
- Preferences store local UI/session lifecycle flags (`hasStarted`, `appLockEnabled`, `rememberSession`, `signOutPending`) and random WebKit store identifiers (`websiteDataStoreID`, `pendingSignOutStores`). They contain no Instagram password or session token. The existing privacy manifest's preferences-access reason applies to these settings; the manifest describes the native app, not Instagram's collection.
- The Stories DOM filter uses an isolated JavaScript world, which separates JavaScript namespaces but shares the DOM. Its bridge accepts only supported state strings and a temporary opaque location token from the current filtered view's main frame on an allowed HTTPS Instagram origin. The token contains no destination or account data and is validated against the current isolated-world document before changing native display state. It has no credential, file, media, or arbitrary-execution command.

## Navigation and filtering

- Main-frame navigation permits only HTTPS, exact `instagram.com` / `www.instagram.com` hosts, default TLS ports, no embedded credentials, and reviewed authentication, Stories, and Direct inbox/thread/new-message routes. Ambiguous encoded paths and unsupported routes are refused. TLS authentication is not overridden.
- Stories document subframes must stay on those same Instagram origins. Authentication and Messages additionally permit the exact HTTPS `www.facebook.com/instagram/login_sync` path, with an optional trailing slash, only for a subframe initiated by an allowed Instagram origin. This path was observed in Instagram's live verification flow and Direct initialization on the connected iPhone. It does not permit Facebook top-level navigation, other Facebook paths, or a Facebook native-message bridge. Navigation responses revalidate frame destinations after redirects, require displayable HTML, and reject attachments. No third-party challenge provider is currently verified or allowed; unsupported verification frames remain blocked and the user can try another Instagram-provided method. Adding a provider requires review of its exact origins and paths.
- Login and Messages permit exact `about:blank` and `about:srcdoc` subframe initialization only when WebKit identifies the creator as an allowed HTTPS Instagram origin. These local documents inherit that origin. This exception does not allow top-level local documents, untrusted creators, or external provider requests.
- App-Bound Domains restricts top-level navigation; it does not protect third-party iframes or block every network resource. Instagram still loads its own resources, CDN media, tracking, and ordinary network requests.
- External HTTPS navigation requires a user link action and native confirmation, then opens in the default browser outside this app's session. Custom schemes, automatic external redirects, and downloads are refused.
- Stories pages stay hidden until the document-start filter reports an allowed display state. Unknown layouts and failed filter installation remain hidden. Authentication pages are displayed by native navigation state without installing that filter. Filtering is a best-effort control for changing web UI, not a security boundary against hostile page code.
- Viewer detection requires visible media in a recognized viewer. A home-page overlay requires a recognized Story tap. Loading and failure states expose native recovery actions rather than revealing the entire page.
- When an opened viewer disappears or finishes, the filter reuses a visible home tray or reports `story-ended`. Native code accepts this only during a Story session on an allowed home/Story route and loads the fixed Instagram home URL. The message cannot supply a destination; outgoing viewer messages are ignored until the new document commits.
- Direct navigation is restricted to the inbox, numeric thread paths, and the new-message route. Messaging readiness requires recognized Instagram regions; global navigation and unrelated content remain hidden. The bridge reports readiness only, never conversation identifiers, participants, drafts, or message contents. Message history, rendering, sending, and storage remain within Instagram/WebKit. Remembered sessions return to the inbox after backgrounding instead of restoring an open thread.
- Camera/microphone capture, automatic JavaScript windows, link context menus, and back/forward gestures are disabled. There is no media downloader or custom network client.

## Device lock and session lifetime

**Require device unlock** is optional and recommended during onboarding for remembered logins. It uses Apple's device-owner authentication with device-passcode fallback; enabling or disabling it requires successful authentication. The app retains and invalidates its authentication context, rejects stale or cancelled results, and applies success only while foregrounded. A system authentication prompt may temporarily make the app inactive; its result waits for the active scene. Backgrounding invalidates the attempt and locks the app again when protection is enabled.

The browser is created or restored only while the scene is active and unlocked. Inactivity suspends media and covers content, including the Settings sheet; dialogs and Settings are dismissed when backgrounding or locking. Settings and external-link actions are disabled while access is denied. Temporary authentication-prompt inactivity keeps Settings available after successful authentication. Backgrounding detaches Stories/Messages views, removes their bridge/scripts and observations, and cancels timers.

In a remembered session, a completed unscripted authentication document is stopped and parked offscreen in memory when backgrounding, preserving a challenge while the user retrieves an authenticator code. The published browser reference is cleared; document-navigation delegates remain attached and reject actions/responses while access is denied. Restoration requires active, unlocked access and revalidates the parked URL because page history can still change locally. Authentication history changes preserve a committed login document without a filter bridge. Unsupported parked routes remain hidden, and content routes get a fresh filtered browser. Sign-out and session-preference changes discard parked views. WebKit process termination discards the document and defers a fresh allowed authentication load until access is granted. No form content or authentication URL is written to native preferences, and a parked document does not survive application termination.

**Remember Instagram login** defaults on to preserve existing behavior. Remembered sessions use an app-specific persistent WebKit store and can restore after unlocking. Turning the preference off uses `WKWebsiteDataStore.nonPersistent()`: backgrounding clears and detaches the private session, and relaunch does not restore it. Changing Remember Instagram login in either direction clears the current local session. Nonpersistent storage is not a claim about forensic erasure, operating-system backups, or Instagram's own retention.

## Local sign-out and account protection

Before awaiting website-data deletion, sign-out records pending cleanup, clears saved session references, invalidates the current browser generation, and detaches the web view. A new login receives a new persistent store identifier or a new nonpersistent store, so it cannot select the recorded old session. Later foreground startup retries queued store deletion; a failed removal retains its identifier for future retries without restoring that store. WebKit data removal covers cookies, caches, and website storage. These lifecycle controls address interrupted cleanup, without claiming that preferences writes are a transaction or that deletion guarantees forensic erasure.

Local sign-out does not revoke a session at Instagram or sign out other devices. Settings explains Instagram's own **Accounts Center → Password and security → Where you're logged in** controls, and recommends an authentication app for Instagram two-factor protection plus saved recovery codes. Device unlock and Instagram two-factor authentication protect different access points. Some accounts call Accounts Center **Meta Account** during Meta's [rollout](https://about.fb.com/news/2026/04/meta-account/).

## Verification and changes that need review

Regression tests exercise delayed/cancelled authentication, inactive-to-active success, interrupted background attempts, protected preference changes, unscripted authentication configuration, access-gated restoration, private-session background cleanup, pending sign-out recovery, and strict document-frame/redirect response validation. Existing WebKit fixtures check Stories visibility, viewer transitions, messaging readiness and interactions, script/native route agreement, and fail-closed filtering. Passing fixtures does not establish compatibility with a live Instagram account.

Physical-device checks must cover Instagram MFA/recovery flows, lock restoration before browser loading, backgrounding during authentication, privacy coverage over Settings and each native dialog, private-session background/relaunch behavior, and termination during sign-out. See [README.md](README.md) for the test commands and device checklist.

Treat new hosts/routes or challenge providers, content extraction, network libraries, analytics, bridge messages, authentication-page DOM handling, and lifecycle persistence changes as security-sensitive. Keep regression tests passing and confirm live behavior on a device. Unsupported layouts or verification providers must remain blocked rather than widening access as a fallback.
